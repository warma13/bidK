# 拍卖之王 — 多人联机方案

## 一、单机流程总览

先完整梳理当前单机版的玩家操作路径，作为联机改造的基础。

### 1.1 全局流程图

```
启动 → 开始界面 → 加载存档/金币
                      ↓
                   主菜单
                   ├─ [竞拍] → 区域选择 → 竞拍大厅(选角色+选场次) → (地图抽选) → 对局 → 结算 → 返回大厅
                   ├─ [仓库] → 查看已有物品
                   ├─ [富豪榜] → 排行榜
                   └─ [设置/奖励]
```

### 1.2 各阶段详细说明

#### 阶段 1：区域选择（MapScreen）

全屏地图展示 3 个区域，玩家点击区域标记进入该区域的竞拍大厅。

| 区域 | 场次 | 入场费 | 入场门槛 | 期望价值 |
|------|------|--------|---------|---------|
| 旧城商业区 | 简单 | 免费 | 无 | 3 万 |
| 旧城商业区 | 普通 | 5 千 | 无 | 10 万 |
| 科技产业园 | 50 万场 | 2.5 万 | 有资产要求 | 50 万 |
| 科技产业园 | 200 万场 | 4 万 | 有资产要求 | 200 万 |
| 港口保税区 | 1000 万场 | 8 万 | 有资产要求 | 1000 万 |
| 港口保税区 | 5000 万场 | 20 万 | 有资产要求 | 5000 万 |

**关键约束：不同区域/场次的入场门槛不同（资产要求、入场费），玩家必须先选区域和场次。**

#### 阶段 2：竞拍大厅（LobbyScreen）

角色选择、场次选择、开始按钮在同一个界面中完成：

1. **角色选择**（左侧）：11 个角色，各有不同专精品类和技能
2. **场次选择**（右侧）：该区域下的难度档位（如简单/普通），显示入场费和资产要求
3. **道具配置**（右下）：预留功能

点击「开始行动」→ 校验入场费和资产 → 进入地图抽选或直接开始对局。

#### 阶段 3：地图抽选（MapSelectionScreen）

当区域有多种仓库类型时触发（如科技产业园有 techpark 和 datacenter 两种）。

老虎机动画随机选定一种仓库类型，3.5 秒后揭晓结果。单仓库类型的区域跳过此步。

#### 阶段 4：对局（5 轮暗标竞拍）

4 位竞拍者（单机模式：1 人类 + 3 AI）进行最多 5 轮暗标竞拍：

```
每轮循环：
  信息揭露 → 暗标出价（30/60 秒） → 出价揭示 → 倍率判定
     ↓                                            ↓
  角色技能揭示                              有赢家 → 开箱
  公开信息                                  无赢家 → 下一轮
                                           第 5 轮平局 → 实时竞拍（8 秒）
```

**倍率门槛**：第 1-4 轮要求最高价/第二名 ≥ 2.0/1.6/1.4/1.2 倍，第 5 轮严格大于即可。

#### 阶段 5：开箱

赢家的仓库物品逐个揭示（品质越高动画越慢），实时累加战利品价值。

#### 阶段 6：结算（GameOverDialog）

- **赢家**：查看物品列表，可按品质筛选快捷回收，剩余物品入库
  - 回收价值 = 物品的 `realValue`（即物品真实价值，不打折）
  - 仓库空间不足时自动回收：按品质从低到高逐个移除，直到剩余物品放得下
- **输家**：领取安慰奖（赢家亏损额 × 10%）
- 点击返回 → 物品入库 + 保存存档 + 回到竞拍大厅

## 二、联机核心问题：什么时候开始匹配？

### 2.1 问题分析

联机的核心是把 AI 替换为真人玩家。但匹配需要一个前提：**所有玩家必须在同一个区域 + 同一个场次**，因为不同场次的入场费、初始资金、仓库价值完全不同。

### 2.2 方案：在大厅点击「开始行动」时发起匹配

角色选择、场次选择和开始按钮在同一个页面（竞拍大厅），玩家配置好一切后点击「开始行动」触发匹配。

**流程对比**：

```
单机流程：
  区域选择 → 大厅（选角色 + 选场次 + 开始） → 地图抽选 → 对局

联机流程：
  区域选择 → 大厅（选角色 + 选场次 + 开始行动）
                                     ↓
                             【发起匹配】→ 匹配等待
                                     ↓
                             匹配成功（15秒超时AI补位）
                                     ↓
                             地图抽选动画（服务端选定，客户端播放）
                                     ↓
                                   对局
```

### 2.3 为什么这样设计

| 决策点 | 理由 |
|--------|------|
| 角色在匹配前选 | 角色、场次、开始在同一个界面，保持现有 UI 不变 |
| 区域 + 场次决定匹配队列 | 入场门槛不同，必须保证同局玩家条件一致 |
| 仓库类型由服务端决定 | 匹配成功后服务端随机选定，复用现有随机逻辑 |

### 2.4 匹配队列设计

每个「区域 + 场次」组合是一个独立的匹配队列：

```
匹配队列：
  旧城商业区 · 简单    → 队列 A
  旧城商业区 · 普通    → 队列 B
  科技产业园 · 50万场  → 队列 C
  科技产业园 · 200万场 → 队列 D
  港口保税区 · 1000万场 → 队列 E
  港口保税区 · 5000万场 → 队列 F
```

共 6 个匹配队列。角色选择不影响队列分配，同队列内的玩家可以选择相同或不同的角色。

## 三、联机完整流程

### 3.1 全局流程图

```
启动 → 开始界面 → 加载存档/金币（clientCloud）
                      ↓
                   主菜单
                      ↓
                [点击竞拍]
                      ↓
               区域选择（MapScreen）
                      ↓
               竞拍大厅（LobbyScreen）
                  选角色 + 选场次（界面不变）
                  点击「开始行动」
                      ↓
                  本地校验入场费/资产
                      ↓
              【发起匹配 C_JOIN_ROOM】
                  发送 { regionId, diffIdx, charIdx }
                      ↓
               匹配等待（覆盖在大厅上的等待提示）
                  显示"正在匹配 2/4..."
                  可取消
                      ↓
               15 秒内凑齐？
                ├─ 凑齐 4 人真人 → 创建房间
                ├─ 超时 → AI 补位至 4 人 → 创建房间
                └─ 用户取消 → 回到大厅
                      ↓
             【匹配成功】
                      ↓
              服务端选定仓库类型（复用现有随机逻辑）
                      ↓
              地图抽选动画（客户端播放，多仓库类型时）
                      ↓
              对局开始（服务端驱动，1~4 真人 + AI 补至 4 人）
              ┌────────────────────────┐
              │ 信息揭露 → 暗标出价     │
              │ → 出价揭示 → 倍率判定   │  ×最多5轮
              │ → (实时竞拍)            │
              └────────────────────────┘
                      ↓
              开箱揭示（服务端逐个推送）
                      ↓
              结算阶段
                赢家：按品质筛选回收 → 剩余入库
                输家：领取安慰奖
                      ↓
              返回主菜单
```

### 3.2 各阶段客户端/服务端职责

#### 阶段 1：区域选择 + 竞拍大厅（客户端本地）

```
客户端：
  1. 显示地图，玩家点击区域 → 进入大厅
  2. 大厅界面不变：左侧选角色，右侧选场次
  3. 点击「开始行动」→ 本地校验入场费/资产
  4. 校验通过 → 发送 C_JOIN_ROOM { regionId, diffIdx, charIdx }
  5. 大厅上方覆盖匹配等待提示

服务端：
  （此阶段无参与）
```

**与单机差异**：「开始行动」从"直接开局"变成"发起匹配"，大厅界面本身不需要改动。

#### 阶段 2：匹配等待（客户端等待，服务端调度）

```
客户端：
  1. 在大厅界面上覆盖匹配等待提示（当前人数 / 等待时间）
  2. 可取消匹配 → 发送 C_LEAVE_ROOM → 回到大厅

服务端：
  1. 收到 C_JOIN_ROOM → 二次校验入场费/资产（防客户端篡改）
  2. 将玩家加入对应队列（regionId + diffIdx）
  3. 队列凑齐 4 人 → 创建房间
  4. 超时（15秒）未凑齐 → AI 补位至 4 人 → 创建房间
     - AI 角色由服务端随机分配（复用现有 AIPlayer 逻辑）
     - AI 出价策略复用现有 AI/Strategies.lua
  5. 广播 S_ROOM_STATUS { players[], countdown } 通知匹配进度
  6. 创建房间后 → 发送 S_GAME_INIT 给所有真人玩家
```

**匹配配置**：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| match_timeout | 15 秒 | 匹配超时时间 |
| player_number | 4 | 每局总人数 |
| desc_name | free_match_with_ai | 超时 AI 补位 |

#### 阶段 3：地图抽选（服务端选定，客户端播放动画）

```
服务端：
  1. 根据区域的 warehouseTypes 配置，随机选定一种仓库类型
     - 复用现有 MapSelectionScreen 的随机逻辑（移到服务端执行）
  2. 通过 S_GAME_INIT 或 S_MAP_SELECTED 告知客户端选定结果

客户端：
  1. 如果区域有多种仓库类型 → 播放老虎机抽选动画（结果已预定）
  2. 如果只有一种 → 跳过动画
  3. 动画结束 → 进入对局
```

#### 阶段 4：对局（服务端权威）

所有游戏逻辑由服务端驱动，客户端只提交操作 + 展示结果。

```
服务端每轮驱动：
  1. 信息揭露
     - 计算公开信息 → 广播 S_INFO_REVEALED
     - 计算各真人玩家的私密线索 → 单播 S_PRIVATE_INFO

  2. 暗标出价
     - 广播 S_BID_START { timer }
     - 收到真人 C_SEALED_BID { amount } → 校验合法性 → 记录
     - AI 使用现有策略异步决策 → 记录
     - 全员出价 或 倒计时结束 → 未出价的真人视为弃权/出价0

  3. 出价揭示
     - 广播 S_BID_REVEALED（逐个，间隔 1 秒）

  4. 倍率判定
     - 计算倍率，判定胜负
     - 广播 S_JUDGE_RESULT
     - 有赢家 → 扣款 → 进入开箱
     - 无赢家 → 下一轮
     - 第 5 轮平局 → 实时竞拍

  5. 实时竞拍（如有）
     - 广播 S_TIEBREAK_START
     - 收到 C_TIEBREAK_BID → 校验 → 广播 S_BID_PLACED
     - AI 使用现有策略决定是否跟进
     - 倒计时结束 → 最后出价者获胜

客户端：
  - 收到服务端事件 → 更新本地只读状态 → UI 响应
  - 玩家操作 → 发送 C_SEALED_BID / C_TIEBREAK_BID / C_USE_SKILL
```

#### 阶段 5：开箱（服务端推送）

```
服务端：
  - 逐个发送 S_ITEM_REVEALED { itemIndex, item }（按品质控制间隔）
  - 收到 C_SKIP_WAREHOUSE → 一次性发送所有剩余物品
  
客户端：
  - 收到物品信息 → 播放揭示动画 → 累加价值
  - 点击"跳过动画" → 发送 C_SKIP_WAREHOUSE
```

#### 阶段 6：结算（服务端处理持久化）

**核心原则：服务端保证数据不丢失，无论玩家是否在线。**

```
服务端：
  1. 广播 S_GAME_OVER（含赢家、物品列表、利润等）
  2. 输家处理（立即执行，无需等待）：
     - 计算安慰奖 = 赢家亏损额 × 10%（赢家没亏则为 0）
     - 通过 serverCloud 给输家加安慰奖
  3. 赢家处理（等待玩家操作，60 秒超时）：
     a. 赢家在线且操作：
        - 收到 C_RECYCLE_ITEMS { rarities } → 
          按品质筛选物品（复用 RecycleManager.FilterByRarity）→
          计算回收价值（复用 RecycleManager.GetRecycleValue，= realValue）→
          回复 S_RECYCLE_RESULT { recycledItems, totalValue, remainingItems }
        - 收到 C_LEAVE_SETTLE → 
          剩余物品尝试入库 →
          空间不足则自动回收低品质（复用 RecycleManager.AutoRecycleForFit）→
          通过 serverCloud 写入物品和金币 →
          回复 S_SETTLE_COMPLETE { storedItems, autoRecycledItems, autoRecycledValue }
     b. 赢家断线或超时（60秒）：
        - 服务端自动执行：全部物品尝试入库
        - 空间不足自动回收（同上）
        - 通过 serverCloud 写入，保证数据不丢失
  4. 通过 serverCloud 统一写入：
     - 金币变动（扣除出价 + 回收收入 / 安慰奖）
     - 物品入库（更新存档）
     - 统计数据更新（总场次、胜场、累计利润）
     - 排行榜更新

客户端：
  - 赢家在线：显示物品列表 + 品质筛选 + 回收按钮，操作后发送给服务端
  - 输家：显示安慰奖金额 → 点击领取返回
  - 收到 S_SETTLE_COMPLETE → 刷新 clientCloud 数据 → 返回主菜单
  - 断线后重连 → 服务端已处理完毕 → 直接刷新数据回到主菜单
```

## 四、匹配模式选择

### 4.1 推荐配置

```json
{
  "multiplayer": {
    "enabled": true,
    "max_players": 4,
    "match_info": {
      "desc_name": "free_match_with_ai",
      "player_number": 4,
      "match_timeout": 15,
      "immediately_start": false
    }
  }
}
```

| 参数 | 值 | 理由 |
|------|-----|------|
| `desc_name` | `free_match_with_ai` | 超时后 AI 补位，避免玩家等太久 |
| `player_number` | 4 | 竞拍固定 4 人 |
| `match_timeout` | 15 | 15 秒内匹配不到就 AI 补位 |
| `immediately_start` | false | 需要凑齐人（或 AI 补位后）再开始 |

说明：`max_players` 是每局房间的人数上限，不是服务器总容量。平台匹配服务可同时处理大量玩家，同一时间可以有很多个房间并行运行。

### 4.2 为什么不用 persistent_world

持久世界模式适合 MMO / 沙盒（服务器常驻，玩家随进随出）。竞拍游戏有明确的开始和结束，是典型的**对局制**，用 `match_info` 更合适。

### 4.3 为什么不用 background_match

后台匹配适合"边玩边等"的场景。竞拍游戏在大厅选完角色和场次后点击开始，直接显示匹配等待即可，没有"边玩边等"的需求。

## 六、事件协议

### 6.1 客户端 → 服务端

| 事件 | 数据 | 时机 |
|------|------|------|
| `C_JOIN_ROOM` | `{ regionId, diffIdx, charIdx }` | 大厅点击「开始行动」 |
| `C_LEAVE_ROOM` | `{}` | 取消匹配 |
| `C_SEALED_BID` | `{ amount, useSkill }` | 暗标出价 |
| `C_TIEBREAK_BID` | `{ amount }` | 实时竞拍出价 |
| `C_USE_SKILL` | `{}` | 使用主动技能 |
| `C_SKIP_WAREHOUSE` | `{}` | 跳过开箱动画 |
| `C_RECYCLE_ITEMS` | `{ rarities }` | 结算：按品质回收 |
| `C_LEAVE_SETTLE` | `{}` | 结算：完成回收离开 |
| `C_REQUEST_STATE` | `{}` | 断线重连请求 |

### 6.2 服务端 → 客户端

| 事件 | 数据 | 说明 |
|------|------|------|
| `S_JOIN_RESULT` | `{ ok, error? }` | 加入匹配结果 |
| `S_ROOM_STATUS` | `{ players[], countdown }` | 匹配进度更新 |
| `S_GAME_INIT` | `{ mySlot, players[], warehouse, config }` | 匹配成功，游戏初始化 |
| `S_PHASE_CHANGE` | `{ phase, round, timer }` | 阶段变更 |
| `S_INFO_REVEALED` | `{ round, items[] }` | 公开信息揭示 |
| `S_PRIVATE_INFO` | `{ skillItems[] }` | 私密线索（单播给对应玩家） |
| `S_BID_START` | `{ timer }` | 暗标开始 |
| `S_BID_CONFIRMED` | `{ playerIdx }` | 某人已出价（不透露金额） |
| `S_BID_REVEALED` | `{ playerIdx, amount }` | 揭示出价（逐个） |
| `S_JUDGE_RESULT` | `{ result }` | 倍率判定结果 |
| `S_TIEBREAK_START` | `{ players[], startBid, timer }` | 实时竞拍开始 |
| `S_BID_PLACED` | `{ playerIdx, amount }` | 实时竞拍中有人出价 |
| `S_ITEM_REVEALED` | `{ itemIndex, item }` | 开箱揭示物品 |
| `S_MONEY_UPDATE` | `{ playerIdx, money }` | 金币变动 |
| `S_GAME_OVER` | `{ winner, players[], warehouseTotalValue, settleTimeout }` | 对局结束 |
| `S_RECYCLE_RESULT` | `{ recycledItems[], totalValue, remainingItems[] }` | 回收结果 |
| `S_SETTLE_COMPLETE` | `{ storedItems[], autoRecycledItems[], autoRecycledValue }` | 入库完成 |
| `S_FULL_STATE` | 完整快照 | 断线重连状态恢复 |

## 七、服务端架构

### 7.1 模块划分

```
Server.lua              连接管理 + 事件路由
    ↓
MatchQueue.lua          匹配队列（6 个队列，按区域+场次）
    ↓
RoomInstance.lua         单局游戏实例
    ↓
┌──────────────────────────────────────┐
│ 每房间独立副本（隔离，复用现有模块）      │
│ GameState · AuctionEngine             │
│ AIPlayer · SkillSystem                │
│ MoneyManager · InfoSystem             │
│ WarehouseGenerator · RecycleManager   │
└──────────────────────────────────────┘
```

### 7.2 核心原则

| 原则 | 说明 |
|------|------|
| 服务端权威 | 所有游戏逻辑由服务端执行，客户端只提交操作 + 展示 |
| 客户端无写 | 对局内金币/物品变动由服务端通过 serverCloud 写入 |
| 事件驱动 | 客户端通过事件接收状态变更，不轮询 |
| 房间隔离 | 每个房间独立模块副本，多房间并行不干扰 |
| 数据不丢失 | 玩家断线/超时，服务端自动完成结算和入库 |

### 7.3 可复用的现有模块

| 模块 | 复用方式 |
|------|---------|
| `GameState.lua` | 服务端直接使用，驱动对局状态机 |
| `AuctionEngine.lua` | 服务端直接使用，驱动竞拍流程 |
| `AIPlayer.lua` + `AI/Strategies.lua` | 服务端控制 AI 出价决策 |
| `WarehouseGenerator.lua` | 服务端生成仓库 |
| `InfoSystem.lua` | 服务端计算信息揭示 |
| `SkillSystem.lua` | 服务端计算技能效果 |
| `RecycleManager.lua` | 服务端执行回收（GetRecycleValue、FilterByRarity、AutoRecycleForFit） |
| `Config.lua` | 客户端/服务端共享配置 |

## 八、断线重连

### 8.1 对局中断线

```
玩家断线
    ↓
服务端：标记该槽位为"断线"，AI 临时接管出价
    ↓
30 秒内重连？
  ├─ 是 → 客户端发送 C_REQUEST_STATE
  │       服务端发送 S_FULL_STATE（当前完整游戏快照）
  │       客户端恢复 UI 状态，继续游戏
  └─ 否 → AI 永久接管该槽位直到对局结束
```

### 8.2 结算中断线

```
赢家在结算阶段断线
    ↓
服务端等待 60 秒超时
    ↓
自动执行：
  1. 全部物品尝试入库
  2. 空间不足 → 按品质从低到高自动回收（RecycleManager.AutoRecycleForFit）
  3. 通过 serverCloud 写入金币和物品
    ↓
数据安全落地，不丢失
    ↓
玩家下次上线 → clientCloud 自动同步最新数据
```

## 九、反作弊

联机模式下服务端天然是反作弊屏障：

| 项目 | 单机 | 联机 |
|------|------|------|
| 出价校验 | 客户端 SecureValue | 服务端校验（金额 ≤ 持有金币） |
| 金币变动 | clientCloud（客户端写） | serverCloud（服务端写） |
| 物品生成 | 客户端生成 | 服务端生成，客户端看不到内容 |
| 技能效果 | 客户端计算 | 服务端计算，私密信息单播 |
| 回收定价 | 客户端计算 | 服务端计算（RecycleManager） |

## 十、实现步骤

### 第一步：基础架构搭建

```
1. main.lua 三路分发
   - IsServerMode() → require("network.Server")
   - IsNetworkMode() → require("network.Client")
   - else → require("network.Standalone")  （已有）

2. Server.lua 骨架
   - Start() 入口，创建场景
   - 注册所有 C_* 远程事件监听
   - 连接/断开管理

3. Client.lua 骨架
   - Start() 入口，加载闸门（等 lobby + clientCloud 就绪）
   - 注册所有 S_* 远程事件监听
   - Send* 系列发送方法
```

### 第二步：匹配流程

```
4. MatchQueue.lua
   - 6 个队列（区域+场次组合）
   - Add(queueKey, connection, userId, charIdx)
   - Tick() 定时检查：凑齐4人创建房间 / 超时AI补位
   - Remove() 取消匹配

5. C_JOIN_ROOM → S_ROOM_STATUS → S_GAME_INIT 链路打通
   - 客户端发起 → 服务端入队 → 凑齐后广播初始化

6. 大厅 UI 改动
   - 「开始行动」改为发送 C_JOIN_ROOM
   - 覆盖匹配等待提示（人数/倒计时/取消按钮）
```

### 第三步：房间实例 + 对局驱动

```
7. RoomInstance.lua
   - 封装一局游戏的完整生命周期
   - 持有独立的 GameState / AuctionEngine / AIPlayer 等模块副本
   - 管理玩家槽位（真人/AI标记）

8. 现有模块适配
   - GameState / AuctionEngine：去掉直接操作 UI 的代码，改为触发事件
   - 单机模式下事件直接调用 UI（保持兼容）
   - 联机模式下事件通过网络发送给客户端

9. 仓库生成 + 地图抽选
   - 服务端调用 WarehouseGenerator（复用现有逻辑）
   - S_GAME_INIT 带上 warehouseTypeId
   - 客户端收到后播放抽选动画
```

### 第四步：对局通信

```
10. 暗标出价
    - 客户端：C_SEALED_BID { amount, useSkill }
    - 服务端：校验金额 → 记录 → 全员出价后广播 S_BID_REVEALED

11. 信息揭露
    - 服务端：InfoSystem 计算 → 广播 S_INFO_REVEALED（公开）
    - 服务端：SkillSystem 计算 → 单播 S_PRIVATE_INFO（私密）

12. 实时竞拍
    - C_TIEBREAK_BID → 校验 → 广播 S_BID_PLACED
    - AI 跟进逻辑（复用 Strategies.lua）

13. 开箱
    - 服务端逐个发送 S_ITEM_REVEALED
    - 客户端 C_SKIP_WAREHOUSE → 批量发送剩余

14. ClientGameState.lua
    - 客户端只读状态镜像
    - 收到 S_* 事件 → 更新状态 → UI 响应
```

### 第五步：结算 + 持久化

```
15. 结算通信
    - C_RECYCLE_ITEMS → 服务端 RecycleManager 执行 → S_RECYCLE_RESULT
    - C_LEAVE_SETTLE → 服务端入库 + 自动回收 → S_SETTLE_COMPLETE

16. serverCloud 写入
    - 金币变动（入场费扣除、出价扣除、回收收入、安慰奖）
    - 物品入库（存档格式复用 SaveSystem 的压缩编码）
    - 统计数据 + 排行榜更新

17. 断线保护
    - 结算超时60秒 → 服务端自动入库
    - 对局中断线 → AI 接管 → 结算时仍归该玩家
```

### 第六步：断线重连

```
18. 对局中重连
    - C_REQUEST_STATE → 服务端发送 S_FULL_STATE（完整快照）
    - 客户端恢复 UI 到当前阶段

19. 测试 + 打磨
    - 单机/联机双模式并行测试
    - 匹配超时边界情况
    - 多人同时出价的并发处理
```
